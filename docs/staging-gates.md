# Required staging verification before step 3

The schema/private buckets, real SQL policies, concurrent reservation, deployed username login, session refresh/recovery/logout, Data API and private Storage checks now pass. Final evidence is archived in `test/results/` and summarized in `docs/refactor-progress.md`. The checklist below describes the full gate and remaining operations; email delivery, backup/restore, capacity and production acceptance are still pending.

1. Create or select an isolated Supabase staging project with the owner-approved region and put its configuration in `env/staging.env`. Apply the versioned migrations with Supabase CLI to staging. Use the direct database connection for protected provenance staging; never browser keys for imports.
2. Verify that Auth registration uses the controlled username reservation. Default/public Auth signup must fail without a valid unexpired reservation. Test two independent concurrent claims for one normalized username: one succeeds, the other receives unavailable. Test a failed signup and reservation expiry. Confirm email verification, redirect allowlists, recovery delivery, and session refresh using real Supabase Auth before accepting step 3.
3. Run protected reads/mutations using real anonymous, participant A/B, assigned/unassigned researcher, and administrator identities. Exercise direct Data API requests and Storage signed download issuance, not only UI redirects. Service-role keys must stay in server/import environments. The private schema must not appear in exposed API schemas.
4. Verify private `legacy-archive`/`exports` buckets cannot be fetched anonymously or by an unrelated participant. Test that a scoped artifact grants access only to its intended account/study. Keep archive filenames and manifests outside static build roots.
5. Exercise the run creation and ingestion RPCs through authenticated HTTP calls. Repeat a batch with identical and changed payloads, send a malformed final event to establish transaction rollback, revoke enrollment, switch accounts, and attempt completion while records are missing. Verify no unauthorized rows or false completion transitions occur.
6. Configure database backups/PITR as supported by the selected project and capacity. Independently copy private Storage objects and checksum manifests to a protected recovery destination. Restore a database backup into an isolated project, restore Storage separately, and verify object hashes plus database artifact links. Record the actual observed recovery results; database backups alone do not preserve object bytes.

Later gates include the complete import rehearsal twice, explicit conflict acceptance, browser parity, one-million-logical-trial load measurements, and final delta/cutover. Keep existing writers until those pass; do not dual-write production.

Sources used to review the foundation: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [function authorization](https://supabase.com/docs/guides/functions/auth), [password authentication](https://supabase.com/docs/guides/auth/passwords).
